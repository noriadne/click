# Supabase SQL 관리 규칙

`supabase/` 폴더의 핵심 원칙: **빈 Supabase 프로젝트에서 번호 순서대로 전부 실행하면 현재 운영 DB와 같은 상태가 구축되어야 합니다.** DB 이전(리전 변경, 재해 복구, 새 개발 DB)은 이 폴더만으로 가능해야 합니다.

- DB 구조를 바꾸는 모든 것(테이블, 컬럼, RLS 정책, 트리거, 함수, 인덱스)은 SQL 파일로 남깁니다. 새 변경은 다음 번호 파일(`006_...`)로 추가합니다.
- 기존 파일을 수정해야 할 때는 최소한으로 하고, 수정 후에도 "빈 프로젝트 순차 실행 결과 = 운영 DB 상태"가 유지되는지 확인합니다.
- **SQL Editor에서 직접 바꾼 것도 반드시 파일로 되돌려 반영합니다.** 파일과 실제 DB가 어긋나면(드리프트) 빈 프로젝트 재현이 깨집니다.
- 모든 파일은 재실행해도 안전해야 합니다(`if not exists`, `create or replace`, `drop ... if exists`). 이미 적용된 DB에 다시 실행해도 데이터를 지우거나 에러를 내면 안 됩니다.
- 뒤 번호 파일은 앞 번호 파일의 결과만 참조합니다. 번호 순서를 건너뛰어야 하는 의존성을 만들지 않습니다.
- 파일 상단 주석에 목적, 실행 위치(Supabase SQL Editor), 선행 파일을 적습니다.
- 일회성 데이터 작업(테스트 데이터 삭제, 샘플 INSERT 등)은 이 폴더에 넣지 않습니다. 작업 시점에만 실행하고 `PATCHNOTES.md`나 대화에 남깁니다.
- 데이터를 지우거나 구조를 파괴하는 구문(`drop table`, `drop column`, `delete`, `truncate`)은 실행 전에 사용자에게 영향과 되돌림 가능 여부를 알리고 확인받습니다. 운영 DB에는 특히 주의합니다.
- SQL을 추가·수정하면 `supabase/README.md`의 순서 표를 같이 갱신하고, `PATCHNOTES.md` 항목의 `적용 방법`에 "운영 DB / 개발 DB에 각각 몇 번 파일을 실행해야 하는지"를 적습니다.
- 저는 Supabase에 직접 SQL을 실행할 수 없습니다. 실행은 사용자가 SQL Editor에서 하고, 저는 파일 작성과 실행 안내를 합니다.
- 빈 프로젝트 순차 실행 검증은 사용자가 새 임시 프로젝트나 개발 DB에서 해야 합니다. 검증하지 못했다면 그 사실을 `PATCHNOTES.md`에 적습니다.
